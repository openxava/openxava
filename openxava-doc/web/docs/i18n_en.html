Providing customized labels and messages for your application is done using the i18n files (whether you have multilingual requirements or not -- if not, you only have one version of the file in the primary language of your application).

To show or hide warnings in the logs regarding missing labels or messages, set the property "i18nWarnings" in properties/xava.properties to true or false respectively.

Labels

The label source file(s) are found in the i18n folder of your project, named <app>-labels_<lang>.properties (e.g. MySchool-labels_en.properties), and are copied by the build script into web/WEB-INF/classes folder.

Your labels are applied in addition to the label source files provided by OpenXava project (which are found in the ../OpenXava/i18n folder, are named Labels_<lang>.properties, and are also copied by the build script into your web/WEB-INF/classes folder). If the same entry appears in your file(s) and the OpenXava file(s), the one in your file will be used, which allows you the ability to customize the labels provided by OpenXava.

Comments can be included using # as the first character.

Blank lines are allowed, and can be useful to visually separate things for easier reading.

Application Name

App name and description can be overridden like this:

MySchool=School ABC
MySchool[description]=Welcome to the School ABC application

In general, many OpenXava items in this file can have [description] entries -- in the above example, the standard OX welcome page displays the app description. In most other cases, the [description] text is used for tool-tips that pop up when the mouse is hovered over the field.

Note that if you wish to have a very verbose tooltip, you can embed special characters to help with formatting. Specifically, as of this writing, the newline (\n) and tab (\t) work fine. As an example, this entry

studyId[description]=Unique Identifier per study \n See if this wraps... \n and this...\n\t try a tab....

will produce the expected behavior.

Module Name

Module name labels can be overridden like this:

Classroom.module=Class Room

Field Name

Fields which are used in many places in the application can be overridden globally like this:

addressGroup=Street Address

Specific module field names can be overridden like this:

Classroom.location=Door Badge

For associations, there is often a qualified field, which can be overridden like this:

Project.currentManager.managerName=PM Name

For the default view, so it has only effect in detail mode:

Customer.view.name=Customer Name

For a specific view, for the view named "Simple" in this example:

Customer.views.Simple.name=C Name

In List mode, qualified names are automatically qualified by OpenXava like this: Manager name of Current manager. If this is not desired, it can be overridden like this:

Project.tab.properties.currentManager.managerName=PM Name

or for a specific named Tab like this:

Project.tabs.my_tab_name.properties.currentManager.managerName=PM Name

or globally for all modules like this:

*.tab.properties.currentManager.managerName=PM Name

Enumeration value labels

The labels of an enumeration's values are independent of the label of the property itself. For example, suppose a property named distance uses this Java enum:

public enum Distance { LOCAL, NATIONAL, INTERNATIONAL }

To translate its options, add entries to your application's labels file using propertyName.valueName. The value names can be written in lowercase, even when the Java constants are uppercase:

distance.local=Local delivery
distance.national=National delivery
distance.international=International delivery

Here distance is the property name, not the enum class name Distance. These entries apply to properties named distance; they do not change the property's own label.

To define labels for the values globally, without qualifying them by property name, use:

local=Local
national=National
international=International

The property-qualified label takes precedence over the global value label. For example, distance.local overrides local for the distance property, without changing how LOCAL is labeled in other properties.

Tab titles

A tab defines the list of records in list mode. Its title is used for reports and also in list mode when the title is visible. To customize the title of the default (unnamed) tab, use Entity.tab.title:

Customer.tab.title=Customers report

For a named tab, use Entity.tabs.tabName.title:

Invoice.tabs.Current.title=Invoices report

In this example, Current is the name declared in @Tab(name="Current", ...), not the module name or a view section name. Use tab (singular) for the default tab and tabs (plural) followed by the tab name for a named tab. These entries change the title, not the column headings or the module label.

Tab titles can include positional parameters such as {0}:

Invoice.tabs.DefaultYear.title=Invoices report of year {0}

Supply the value from an action using the tab's API, for example:

getTab().setTitleArgument(Integer.valueOf(2002));

The resulting title is "Invoices report of year 2002". The parameter is not filled automatically from the tab name or its filter. For several parameters, use setTitleArguments(...) with placeholders {0}, {1}, and so on.

Collection column labels

To customize a column heading in a collection, add an entry to your application's <app>-labels_<lang>.properties file using this format:

OwnerEntity.collectionName.propertyPath=Label
  • OwnerEntity: the entity that contains the collection.
  • collectionName: the name of the collection in that entity.
  • propertyPath: the property displayed in the column, relative to the collection element. It can include a reference, such as product.number.

For example, suppose Invoice has a collection named details, declared as an @ElementCollection of InvoiceDetail, an @Embeddable class. Each detail has a product reference, and the collection displays product.number as a column. To label that column "Code" only in the details collection of Invoice, use:

Invoice.details.product.number=Code

Use the owner entity and the collection name, not the class of the collection element. In this example, InvoiceDetail.product.number=Code is not the correct key for the collection column, even though InvoiceDetail defines the product reference. Do not insert tab.properties into the collection-specific key either.

To label product.number globally, rather than only in Invoice.details, use:

product.number=Code

This global label applies wherever that property path is used, unless a more specific label overrides it.

The same collection-specific format applies to collections of entities. For example, to customize the number column of the deliveries collection in Invoice, use:

Invoice.deliveries.number=Delivery number

If a collection-specific label is not defined, OpenXava uses the label from the default tab of the collection element, if one is defined. For example, without Invoice.details.product.number, the label can be defined with:

InvoiceDetail.tab.properties.product.number=Code

Unlike Invoice.details.product.number, this tab label is not restricted to the details collection of Invoice.

@View Section and Group Names

Section and Group names in an @View can be overridden as well. For example, if I have a section name "s_overview" and a group "g_pgm_dates" defined in a @View in Entity Program, the labels can be overridden like this:

Program.s_overview=Overview
g_pgm_dates=Program Milestone Dates

Note that as of OpenXava 5.4, Group names do not seem to support any dot-notation.

Actions

Action button names can be overridden using the format <Controller-name>.<action-name> like this:

ListProjectsForProgram.listProjects=List Projects

Subcontroller labels

A subcontroller groups actions in a menu. To customize the label of that menu, use the controller name alone as the key in your application's labels file:

ColorSub=My processes

For example, this entry labels the menu for a subcontroller declared in controllers.xml as:

<subcontroller controller="ColorSub"/>

The menu label uses the controller name, whereas an individual action label uses Controller.action. For example, ColorSub.firstAction labels an action inside the menu; it does not label the menu itself.

The same rule applies to subcontrollers in collections. For example, if a collection uses @ListSubcontroller("TeamMemberSub"), customize its menu label with:

TeamMemberSub=Stuff

Use the subcontroller name directly; do not prefix it with the owner entity or the collection name.

Organization

The organization name is shown in reports and it is specified with the xava.organization entry, thus:

xava.organization=My Company Inc

Programmatic use

Labels can also be used explicitly from Java code. Define the keys in your application's <app>-labels_<lang>.properties files, with a translation for each language. In the examples below, keys such as entry_full_address are identifiers chosen by the developer, not names that OpenXava derives automatically from a model.

Setting a view or dialog title

To use a translated title, define a label:

entry_full_address=Enter the full address

Then, from an action, pass its key to getView().setTitleId():

getView().setTitleId("entry_full_address");

OpenXava resolves the identifier in the current language. For a dialog, call this after showDialog(), so that getView() refers to the dialog's view. In contrast, getView().setTitle("Enter the full address") sets a literal title without translating it. A title identifier can also refer to an entry in the messages file. See the modal dialog example for a complete action.

Changing property, group and section labels

Use getView().setLabelId(memberName, labelId) to change a label dynamically in the current view. The first argument identifies the property, group or section; the second is a key in the labels file, not the translated text. For example, define:

my_property_name=Invoice number
my_group_name=Delivery information
my_section_name=Incidents and remarks

Then apply the labels from an action:

getView().setLabelId("number", "my_property_name");
getView().setLabelId("deliveryData", "my_group_name");
getView().setLabelId("incidents", "my_section_name");

Here number is a property, and deliveryData and incidents are the group and section names declared in the view. Property names can also be qualified, for example getView().setLabelId("customer.name", "my_customer_name"), with the corresponding label defined in the labels file. These calls change the displayed labels in that view; they do not modify the properties files or the labels globally.

Obtaining a label as a string

Use org.openxava.util.Labels.get() whenever your code needs the translated text of a label, whether in an action, a report, an editor or any other application code. It returns a string and does not require a View or change the user interface.

For example, define:

invoice_ready=Invoice ready

Then obtain the text using the current language or an explicit locale:

import java.util.Locale;
import org.openxava.util.Labels;

// Uses OpenXava's current locale
String text = Labels.get("invoice_ready");
// Uses the explicitly requested locale
String englishText = Labels.get("invoice_ready", Locale.ENGLISH);

The first overload uses Locales.getCurrent(). Outside the normal OpenXava request context, use the overload with an explicit Locale when you need a specific language. You can also supply a fallback text if no label can be resolved:

String text = Labels.get("invoice_ready", Locale.ENGLISH, "Invoice ready");

Messages

The message source file(s) are also found in the i18n folder of your project, named <app>-messages_en.properties (e.g. MySchool-messages_en.properties), and are copied by the build script to the web/WEB-INF/classes folder.

Your messages are applied in addition to the message source files provided by OpenXava project (which are found in the ../OpenXava/i18n folder, are named Messages_<lang>.properties, and are also copied by the build script into your web/WEB-INF/classes folder). If the same entry appears in your file(s) and the OpenXava file(s), the one in your file will be used, which allows you the ability to customize the messages provided by OpenXava.
